### 优先给什么字段追加索引
- 高频查询字段
- JOIN 关联字段
- 排序字段（order by）
- 分组字段（group by）

### 联合索引策略
- 最左匹配原则
```
INDEX(a, b, c)
// 能命中
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3
// 不能高效命中
WHERE b = 2
WHERE c = 3
```
- 联合索引字段顺序
    - 区分度高的放前面
    - 等值查询放前面
    - 范围查询放后面
```
WHERE user_id = 1
AND status = 1
AND create_time > xxx
// 推荐
(user_id, status, create_time)
```

### 不适合加索引的字段
- 区分度太低（列如性别，只有男女两个值）
```
核心原因：索引最大价值是“快速缩小范围”
数据库有100w条数据，可能50w男 50w女，不如直接全表扫描了

不是说区分度低的都不能加，一般可能会和其他字段组成联合索引
比如 (id, status)，查询某个用户，已支付的订单之类的
```
- 经常更新的字段（索引对增删改效率有影响，需要维护B+树）
- 大字段（索引代价大）
```
索引字段值 + 主键id 字段值过大会让B+树高度增高
索引占磁盘巨大
```

### 避免索引失效
- 避免函数操作（如 DATE(create_time)）
- 避免隐式类型转换（如 id = '123'）
- 避免 leading wildcard（如 name LIKE '%abc'）
- 避免 OR 条件（如 WHERE a = 1 OR b = 2，除非 a 和 b 都有索引）

### 覆盖索引（非常重要）
- 索引包含查询的所有字段，避免回表查询（回表是先查询id，再根据id回表里把需要的字段查询出来，若查询的字段都是索引字段，则不需要回表）
```
SELECT id, name
FROM user
WHERE mobile = 'xxx'
// 推荐
CREATE INDEX idx_mobile ON user(mobile, id, name)
```
- 典型例子
```
// 很多大表分页：
// 先覆盖索引查id：
SELECT id
FROM orders
WHERE status = 1
ORDER BY create_time DESC
LIMIT 10000,20
// 然后
SELECT *
FROM orders
WHERE id IN (...)

// 先用覆盖索引缩小范围
// 深分页优化经典方案
```

### 索引不是越多越好
- 多索引会增加维护成本，降低写性能
- 占磁盘
- 降低 insert/update
- 增加锁竞争
